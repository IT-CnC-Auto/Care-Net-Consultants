Orientation

The map in one paragraph

A static site on Vercel, a Postgres database on Supabase, and three ways in. Anyone can read two deliberately public views. A signed in person reaches the framework through row level security. Everything transactional goes through server endpoints that hold the service key, and everything the assistant does goes through one edge function that reads its own settings from the database on every call.

Front end
Static HTML and four serverless endpoints in msp-forge/vercel/, deployed to the Vercel project cnc-msp-forge
Database
Supabase project pboebfnujzffgwctsplw, shared with other Care Net systems. Every object in this build is prefixed msp_ so it is additive and never collides
Assistant
Supabase edge function msp-assistant, one of ten functions on the project
Source of truth
38 migration files in msp-forge/supabase/migrations/. Replaying them into an empty project rebuilds everything
Identity
Supabase Auth magic link. Roles carried in app_metadata.msp_roles: forge_agent, forge_verifier, forge_omp, forge_admin

Access model

Who reaches what

Three lanes, and they do not overlap. The red mark is where each lane stops.

Anyone on the internet

role: anon
  1. Reads msp_public_industry_profile and msp_public_framework_stats with the publishable key
  2. Sees industry names, verified instrument names and gazette applicability notes, role titles, hazard and protocol names, counts
  3. Reaches zero rows of every other table, and no parameter or assistant function
Marketing surface only. No client data, nothing clinical.

A signed in company

Auth user linked to msp_client_account
  1. Signs in by magic link on account.html
  2. Reaches its own account, packs and revisions under row level security
  3. May ask the assistant one action, explain_plan, rate limited per hour
  4. Never reaches the framework tables, the register, or another company's anything
Client access is itself a parameter and can be switched off.

Care Net staff

a forge role in the JWT
  1. Signs in on review.html or settings.html
  2. Reads the framework, the registers and the audit tail by role
  3. forge_omp decides, recommends and signs. forge_admin changes parameters and cuts releases
  4. No role releases a pack without a practitioner signature. The database trigger, not the interface, enforces that
Every function checks the role in its own body. The interface is never trusted.

Supabase, edge tier

The assistant connection

One edge function, msp-assistant, deployed and active. It carries no settings of its own: model, effort, thinking mode, ceilings, limits, prices and the enabled action list are read from the parameter store on every single call.

ActionWho may run itGrounded on
explain_planA signed in client companyThe verified rows for its industry
industry_briefCare Net staffThe verified rows for one industry
triage_otherCare Net staffThe industry codes present in the rows, or none at all
monthly_watchCare Net staff and the agentThe audit report and the verified instrument list

What holds it inside the framework

It answers only from the rows handed to it in the same request, and those rows come from grounding functions that return verified instruments and no client data at all. It may not cite a law, a threshold or an interval that is not in those rows. It may not express an opinion on whether any individual worker is fit for work. Every answer carries the same notice: an explanation of the framework, not a clinical opinion and not a signed plan.

What holds the cost

A preflight call runs before any spend and checks the role, the master switch and the monthly ceiling. Over the ceiling the assistant refuses and says so. Every call lands in the ledger with model, effort, instruction version, tokens, priced cost, latency and outcome, and the refusals are recorded just as carefully as the answers.

One secret outstanding. ANTHROPIC_API_KEY is not set in the Supabase project's function secrets. Until it is, the assistant answers that it is not configured and records the refusal in the ledger. No key was invented, and none is in the repository or the database.

Assurance

Security posture, as tested

Each row below was checked by assuming the role directly in the database or by calling the function as that role. None of it is inferred.

CheckResult
Anonymous reads msp_public_industry_profile17 rows, correct, this is the marketing surface
Anonymous reads msp_legal_instrument, msp_intake, msp_engagement, msp_client_account, msp_draft, msp_audit0 rows each
Anonymous reads msp_env_parameter0 rows
Anonymous calls any parameter or assistant functionRefused at the grant, after migration 037
Anonymous calls msp_ingest_instrumentRefused by row level security on the insert
Anonymous calls msp_kernel_countsReturns zeros, because it can see no rows to count
Parameter change with no identity, or signed in without a forge roleRefused
Parameter set outside its enum, above its ceiling, or to the wrong typeRefused, four separate cases
Attempt to edit a parameter history rowRefused, append only holds
Release a pack without a practitioner signatureRefused by the database trigger, independent of any interface or parameter

The defect worth naming. Postgres grants execute on a new function to PUBLIC by default, so migrations 034 to 036 left the parameter readers callable by the anonymous web role. That was a real exposure, not a theoretical one. The database advisor flagged it, migration 037 revoked it, and the revocation was then verified function by function rather than assumed.
